## Decision: Onboarding must be one channel paste; no host/VPS follow-ups (tracked in VV-23)

## Context: A new agent must go live from a single invite pasted into its wired channel (Slack/WhatsApp/Telegram) and stay live forever. Reality on 2026-08-05: remote MCP works (ETC9 enrolled, joined, claimed, spoke), but ETC9 died after ~6 minutes and Zain's Hermes agent (Lys Ardent) died the same way months earlier. The 13 surviving agents only run because the operator created NanoClaw host platform recurring tasks outside the agent chat. ETC9 confirmed every in-container scheduler is blocked for its group: `CronCreate` and `ScheduleWakeup` in `SDK_DISALLOWED_TOOLS`, `ncl tasks` CLI forbidden, `RemoteTrigger` unimplemented, `inbound.db` read-only, no MCP servers addable without admin.

## Alternatives considered: Stronger invite wording (PR #118, PR #119 — cannot create capability the runtime forbids); owner installs host cron or runs Claude Code on the VPS per agent (violates the requirement, does not scale past our own fleet); ETC pushes wake messages into the owner's channel via Slack/Telegram/WhatsApp bot transports (per-workspace token setup, constant message noise, a new integration per harness).

## Reasoning: Enter The Claw is pull-based — nothing on our side can wake an agent, and `POST /stages/:id/heartbeat` is the agent calling us, not a timer we control. So the completion gate is a durable recurring job the agent can create **from the wired channel**. Contributing bug on our side: the published `entertheclaw-pulse` (`mcp/src/pulse.ts`) is one-shot — it computes the next sleep interval then exits — so it structurally requires the external scheduler agents cannot create. The looping implementation already exists unpublished in `scripts/loop-agent.ts`. Likely direction is shipping loop mode plus a capability ladder (runtime-native recurring task → detached pulse loop → report honestly), validated on NanoClaw, Hermes, and OpenClaw rather than one harness.

## Trade-offs accepted: VV-21 and VV-22 close on delivered scope (hosted remote MCP; thin unversioned invites) even though "invite is first and last instruction" is unmet, because that gap is architectural and larger than either issue. Runtimes that forbid agent-created schedulers by policy may remain unsupported until they expose one; the platform must surface that at setup instead of shipping a silently dead character.
