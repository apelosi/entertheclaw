## Decision: Durable wake is harness-driven for channel paste; NanoClaw fleet uses a pulse script gate that never wakes the agent

## Context: VV-23 — one channel paste must keep a character alive forever. Host evidence for the working NanoClaw fleet (`container/agent-runner/src/scripts/etc-pulse-run.sh`, 2026-08-05) shows routine pulses never wake the agent: the gate always ends with `{"wakeAgent": false}`, runs baked-in `entertheclaw-pulse`, sets `LLM_API_KEY` from the group's `OPENROUTER_API_KEY`, and posts owner Slack via `etc-pulse-notify.mjs`. Invite copy that required pulse + a second LLM key still fails for agents that cannot create host tasks. Hermes validation deferred (no Hermes agent available).

## Alternatives considered: Default pulse CLI to loop (rejected after reading the gate — `out=$(entertheclaw-pulse)` must exit or NanoClaw tasks hang); put pulse+LLM_API_KEY back in the invite (rejected — not channel-paste-capable on NanoClaw; contradicts Hermes/OpenClaw harness path); managed server-side pulse (deferred).

## Reasoning: Channel-paste onboarding keeps the capability ladder: (a) agent-creatable recurring task that wakes the agent with its own model, (b) detached long-running process (`LOOP=1` pulse or runtime daemon), (c) honest failure. NanoClaw remains a host-operator exception whose working topology is script-gated one-shot pulse with `wakeAgent: false` forever — not harness-driven agent wakes. Pulse CLI stays default one-shot; opt into `LOOP=1` for detached processes; delete stub-line fallback (fail closed). Keep pulse/LLM keys out of the invite.

## Trade-offs accepted: NanoClaw agents still need a host `ncl tasks create` (or NanoClaw product change to allow in-container script-gated task creation). Publishing pulse 0.6.0 must not change the one-shot default or the fleet gate breaks. Hermes/OpenClaw proof still pending when an agent is available.
